# 製品と検証のモデル

<a id="product-purpose"></a>
## 製品の目的

Nullstate は、証拠に基づくクラウド攻撃経路検証プラットフォームです。Infrastructure as Code を観測された AWS と Azure の状態と関連付け、ネットワーク、ID、サービス、データの関係を横断して推論し、選択された攻撃経路を制御された環境内で検証し、修正を適用して攻撃を再実行します。

この製品は、クラウドアカウント全体を Terraform で完全に表現することを要求するものではありません。IaC は意図された管理対象の構成を記述し、読み取り専用の探索は実際にデプロイされた状態を記述します。Nullstate は両者を正規化された環境グラフに統合し、各関係の情報源と確信度を保持すべきです。

オープンソース製品は、まず人間、CI ジョブ、コーディング代理向けのローカル DevSecOps 検証フレームワークとして機能すべきです。`nullstate summary --json` は、代理に Markdown レポートの解析を強いる代わりに簡潔な実行結果を提供し、`nullstate context validate` と `nullstate context summary --json` は、実環境のコレクターを追加する前に、安全な読み取り専用クラウドコンテキストの契約を定義します。

<a id="environment-graph"></a>
## 環境グラフ

環境グラフは次の入力を受け入れるべきです。

- Terraform、CloudFormation、CDK のエクスポート、Bicep、ARM、およびプロバイダーの plan/state データ。
- AWS と Azure の読み取り専用リソースインベントリ。
- IAM ロール、Azure RBAC の割り当て、マネージド ID、信頼関係、ワークロード ID。
- AI 代理 ID、代理 ID のブループリント、代理ワークロード ID、委任された利用者コンテキスト、ツール ID、下流の認証情報との関係。
- パブリックエンドポイント、仮想ネットワーク、セキュリティグループ、NSG、ルート、ゲートウェイ、プライベートエンドポイント、ピアリング。
- ストレージ、データベース、秘密管理、コンピューティング、サーバーレス、コンテナ、Kubernetes の構成。
- ネイティブのセキュリティ検出結果、アクティビティログ、フローログ、監査ログ、および選択された実行環境メタデータ。
- 利用者が提供する、または安全なメタデータと合成テストデータから推論する、任意のデータ分類。

グラフはすべてのリソースを複製する必要はありません。セキュリティに関係する経路を特定し、仮説のテストに必要な関係だけを含む最小限の攻撃経路ツインを作成しなければなりません。

現在のコンテキストマニフェストのプレビューは、意図的にローカル限定です。

```bash
nullstate context validate examples/cloud-context/aws-readonly-context.json
nullstate context summary examples/cloud-context/aws-readonly-context.json --json
```

クラウド認証情報を要求せずに、プロバイダー、アカウント、ID、リソース、パブリック公開、データ分類メタデータの構造を検証します。将来のコレクターは、短命の読み取り専用クラウド ID を使い、この契約に準拠したデータを出力すべきです。

<a id="evaluation-and-product-metrics"></a>
## 評価と製品指標

Nullstate のケーススタディにおける価値は、単に説明するだけでなく測定すべきです。現在の評価ハーネスは、再現可能な内部ベンチマークから始まります。

```bash
nullstate eval run examples/eval/iac-security-regression.json --output-dir eval-runs/iac-security-regression
```

ハーネスは、所要時間、検出件数、最高重大度、攻撃の前後の状態、トークン合計、成果物数、期待条件の合格/不合格状態を記録します。これは、Nullstate をスキャナーだけによるレビュー、手動レビュー、汎用コーディング代理によるレビューと比較するための第一歩です。これらのベースラインが存在するまでは、精度や時間短縮に関する広範な主張ではなく、測定された Nullstate の動作に主張を限定すべきです。

<a id="identity-aware-attack-analysis"></a>
## ID を考慮した攻撃分析

開放されたポートや公開コンテナだけで検出結果の全体を説明できるわけではありません。Nullstate は、承認された各攻撃者視点から何に到達できるかを評価すべきです。

| 視点 | 例 |
|---|---|
| 外部 | 匿名のインターネットクライアント |
| テナント利用者 | 認証済みだが低権限のクラウド利用者 |
| 開発者 | デプロイまたは読み取り権限を持つ人間の ID |
| CI ワークロード | GitHub Actions、GitLab、またはビルドシステムの ID |
| 侵害されたワークロード | VM、コンテナ、関数、またはアプリケーションの ID |
| クラウドロール | AWS IAM ロール、Azure サービスプリンシパル、またはマネージド ID |
| AI 代理 | 専用代理 ID、代理ワークロード ID、または代理の実行環境ロール |
| 委任された代理 | 人間の利用者から伝播した権限で動作する代理 |
| 横方向の攻撃者 | 攻撃経路の前段階で取得されたプリンシパル |

各観測結果には、プリンシパル、想定権限、認証方式、対象、到達したデータまたは能力、コマンドによる証拠、確信度を記録すべきです。

<a id="ai-agents-as-cloud-principals"></a>
## クラウドプリンシパルとしての AI 代理

AI 代理は、インフラ、クラウド API、内部サービス、データストア、チケットシステム、ソースリポジトリ、デプロイツールと関わる機会が増えています。次の手段で動作する場合があります。

- 代理専用に作成された専用 ID
- 従来のサービスプリンシパル、マネージド ID、IAM ロール、またはワークロード ID
- 複数の代理が共有する実行環境またはツールの ID
- 人間の利用者から伝播した委任権限
- 下流ツールやサードパーティーサービス向けに取得した認証情報

これらの方式を単一の汎用サービスアカウントにまとめてはいけません。Nullstate は、代理、実行環境、ツール、委任した利用者、認証情報、対象サービスを、別々のグラフノードとして表現すべきです。これにより、誰が操作を開始し、誰の権限が認可し、どのコンポーネントが侵害され得るかを保持します。

代理固有の攻撃経路には次が含まれます。

- プロンプトインジェクションにより代理が正当なクラウド権限を悪用する
- 侵害されたツール、プラグイン、MCP サーバー、メモリ、または取得したコンテンツが操作に影響する
- 過剰な自律性により、意図されたタスクの範囲外で破壊的操作や権限変更を許してしまう
- 信頼できない利用者が高権限の代理に自分のための操作をさせる、混乱した代理人の経路
- 利用者の委任権限で、代理自身の ID ではアクセスできないリソースに到達する
- 共有実行環境 ID により、帰属の特定と最小権限が機能しなくなる
- 代理間の信頼が横方向の移動を可能にする
- 長命または広いスコープの下流認証情報が影響範囲を拡大する

Nullstate は、少なくとも次の三つの権限ビューを別々に評価すべきです。

1. **代理固有の権限：**代理自身の ID で到達できるリソース。
2. **委任権限：**特定の利用者または利用者クラスを代表して動作するときに到達できるリソース。
3. **ツールチェーン権限：**実行環境 ID、プラグイン、ゲートウェイ、コネクター、下流認証情報を通じて到達できるリソース。

レポートは、実効権限の連鎖を説明し、代理、その指示、メモリ、またはいずれかのツールが侵害された場合に公開されるデータと操作を特定すべきです。安全な検証では、本番代理への制御されていないプロンプトインジェクションを試みるのではなく、合成プロンプト、合成データ、制御されたツール、使い捨て環境を使用すべきです。

外部でホストされる代理では、ID 分析だけでは不十分です。Nullstate は実行環境のセキュリティ態勢も評価すべきです。対象には、ワークロードと ID の結合、成果物の来歴、デプロイダイジェスト、ホストと実行環境の完全性、ネットワーク公開、ツール制御、ログ記録、失効、裏付け証拠の鮮度と強さが含まれます。詳細設計は[外部代理の信頼と実行環境のセキュリティ態勢](plans/2026-06-22-external-agent-trust-design.md)にあります。

現在の CLI には、このモデルの初期の決定論的プレビューが含まれます。

```bash
nullstate agent posture verify examples/agent-trust/external-agent-manifest.json
nullstate agent blast-radius examples/agent-trust/external-agent-manifest.json
```

これらのコマンドは、実環境のプロバイダーコレクターではなくローカルマニフェストを対象にします。最初にデータ契約を強化することを目的としており、欠落、陳腐化、または不明な態勢証拠は見える状態のままにし、利用者の委任権限は代理自身の ID と分離しなければなりません。

<a id="exposed-data-and-impact"></a>
## 公開されるデータと影響

クラウド管理者は、重要な内容が含まれていないと考えて、到達可能なサービスを意図的に受け入れる場合があります。それでも Nullstate は、その経路が次を公開するかどうかを特定すべきです。

- オブジェクト名、ディレクトリ一覧、アカウント ID、テナント ID、ホスト名、または内部トポロジー
- アプリケーションログ、バックアップ、診断情報、ビルド成果物、ソースマップ、またはデプロイパッケージ
- 認証情報、トークン、接続文字列、構成、または秘密への参照
- 個人、財務、規制対象、顧客、または専有データ
- 書き込み、削除、なりすまし、実行、またはポリシー変更の能力
- 認証情報への攻撃、横方向の移動、権限昇格、または標的型ソーシャルエンジニアリングを可能にする情報

レポートは次を区別しなければなりません。

- 構成が公開の可能性を示している
- 安全なメタデータが観測された
- 合成の証拠データが取得された
- 高権限の能力が実証された
- 本番の機密コンテンツには意図的にアクセスしなかった

<a id="why-not-attack-production-directly"></a>
## 本番を直接攻撃しない理由

読み取り専用の探索と、承認範囲を厳しく限定した非破壊的検証は、本番に対して実行してもかまいません。自律的なエクスプロイトは、次の理由から制御された環境を既定にすべきです。

1. エクスプロイトは実データを変更、削除、破損、または公開する可能性があります。
2. プローブは、スロットリング、停止、アカウントロックアウト、隔離、またはインシデント対応の起動を引き起こす可能性があります。
3. IAM テストは、永続的な認証情報、信頼関係、または権限変更を作成する可能性があります。
4. データ持ち出しテストは、プライバシー、契約、規制、データ所在地の要件に違反する可能性があります。
5. 本番の依存関係は、承認範囲外の顧客やサードパーティーに影響する可能性があります。
6. クリーンアップで以前の状態を正確に復元できる保証はありません。
7. 繰り返す CI 検証は、決定論的で、ペネトレーションテスターが毎回監督しなくても実行できるほど安全でなければなりません。

安全な運用モデルは次のとおりです。

1. 読み取り専用プロバイダー API を通じて本番を探索する。
2. 攻撃仮説を構築し、優先順位を付ける。
3. ポリシーが許可する場合に限り、許可リストに含まれる非破壊的チェックを本番に対して実行する。
4. 使い捨て環境で合成データを使い、関連する最小限の経路を再構築する。
5. その環境に対して制約付きの攻撃を実行する。
6. 修正を適用し、同じ攻撃を再実行する。
7. 証拠を保持し、実証された経路を回帰テストに変換する。

<a id="aws-and-azure-first"></a>
## AWS と Azure を優先

AWS と Azure は、企業インフラの大きな割合をカバーし、どちらも成熟した IaC エコシステムを持つため、最初のクラウドプロバイダーとすべきです。Terraform は競合する対象ではなく、引き続き第一級の入力です。AWS 向け Terraform と Azure 向け Terraform が意図されたトポロジーと構成を提供し、プロバイダー探索が実環境の状態と管理外のドリフトを提供します。

プロバイダーアダプターは、新たな代理 ID システムもインベントリ化すべきです。Microsoft Entra Agent ID は特化した代理 ID と ID ブループリントを提供し、Amazon Bedrock AgentCore Identity は代理/ワークロード ID の仕組みを通じて代理を表現します。Nullstate は、すべての組織がプロバイダーネイティブの代理プラットフォームを使うと仮定せず、これらの関係を従来のサービスプリンシパル、マネージド ID、IAM ロールとともに取り込むべきです。

プロバイダーに対する正確性は、段階を分けて明示すべきです。

| レベル | 証拠の情報源 | 目的 |
|---|---|---|
| 静的 | IaC、plan、ポリシー、エクスポートされた構成 | 迅速なデプロイ前分析 |
| 観測 | 読み取り専用プロバイダーインベントリとログ | 実際のデプロイ状態を理解する |
| エミュレーション | LocalStack、サービスエミュレーター、コンテナ、またはデジタルツイン | 既知の再現忠実度の限界内で、安全かつ再現可能な検証を行う |
| 実サンドボックス | 使い捨て AWS アカウントまたは Azure サブスクリプション | 最も高い再現忠実度でのエクスプロイト検証 |

各レポートは使用したレベルを特定すべきです。エミュレーターの証拠を、プロバイダーの動作が同一である証明として提示してはいけません。

<a id="ci-cloud-event-and-scheduled-execution"></a>
## CI、クラウドイベント、スケジュール実行

Nullstate は、相互補完する三つのトリガーをサポートすべきです。

<a id="pull-request-and-iac-ci"></a>
### プルリクエストと IaC の CI

Terraform、CloudFormation、Bicep、Helm、ポリシー、または関連するインフラファイルが変更されたときに起動します。

パイプライン：

1. デプロイ前に提案された構成を分析する。
2. 検出結果を承認済みベースラインと比較する。
3. 高リスク変更には、任意で使い捨ての検証環境を作成する。
4. 選択された攻撃経路の回帰テストを実行する。
5. SARIF、機械可読のポリシー結果、証拠成果物をエクスポートする。
6. ポリシーのしきい値を満たさない場合はマージをブロックする。

これは最も速いフィードバックループであり、脆弱な構成がクラウドに到達するのを防ぎます。

<a id="post-deployment-validation"></a>
### デプロイ後の検証

デプロイワークフローが成功した後、またはプロバイダーイベントの後に起動します。

例には、Terraform apply ジョブ、CloudFormation デプロイ、Azure デプロイ、またはセキュリティに関係するリソースやポリシーの変更を示すクラウドイベントがあります。Nullstate は観測された環境グラフを更新し、ドリフトを確認し、影響を受ける安全な検証だけを実行します。破壊的となる可能性のある検証は、更新された本番環境ではなく、使い捨てサンドボックスに振り分けます。

<a id="scheduled-assurance"></a>
### 定期的な保証確認

毎時、毎日、または毎週実行し、コンソールでの手動変更、管理外のリソース、権限ドリフト、新たに公開されたエンドポイント、陳腐化したリスク受容、Git 外の変更が作成した攻撃経路を検出します。

これらのモードは異なる問題を解決します。

- PR CI はデプロイ前に意図された変更を検証します。
- デプロイ後の検証は、観測された状態が期待に一致することを確認します。
- 定期的な保証確認は、ドリフトと通常の経路を外れた変更を捉えます。

成熟した有料プラットフォームは、三つすべてを連携させ、履歴を保持し、チームへ通知し、マネージドなモデル推論を提供できます。オープンソース CLI は、顧客が提供する認証情報とモデルエンドポイントを使用して、引き続きローカルと CI で実行できます。
